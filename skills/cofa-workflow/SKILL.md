# 실무형 과제 진행 순서

이 과제의 목표는 기능 수가 아니라 **합의한 문제 하나를 실제로 해결하고, 그 과정을 설명 가능하게 남기는 것**이다. 작업이 끝난 뒤 사람이 AI 없이 설계 이유·흐름·범위·검증·위험을 설명해야 하므로, 아래 기록을 작업과 동시에 채운다.

## 단계
1. **발굴**: 사람이 실무자와 인터뷰한다. 너는 실무자 발언 원문을 `docs/interview.md`에 남기고 해석을 따로 적는다. 다음에 물어볼 질문을 제안한다. 해법을 먼저 제안하지 않는다.
2. **합의**: 인터뷰 내용으로 `docs/agreement.md` 초안을 쓴다. 성공 기준은 현재값·목표값·측정 방법이 있는 숫자로 쓴다. 사람이 실무자 확인을 받기 전에는 구현하지 않는다.
3. **AGENTS.md 반영**: 합의 내용을 `AGENTS.md`의 1~3절에 옮긴다.
4. **설계**: 구성 요소와 요청 흐름을 `docs/architecture.md`에 적고, 주요 선택(계산 위치, 동기/비동기, 저장 방식, 알고리즘)은 `docs/decisions.md`에 대안·제약과 함께 D#으로 남긴다. 사람 승인 후 진행한다.
5. **뼈대**: 실행되는 최소 구조와 테스트 실행 환경을 만든다.
6. **v0**: 성공 기준 S1을 끝까지 통과하는 가장 작은 흐름을 만든다.
7. **검증·개선**: `verify-and-review` 스킬 절차를 따른다. 탐색·최적화·자동 생성 결과는 생성 코드와 **별개의 검사기**로 규칙 준수를 확인한다.
8. **제출 준비**: `handoff-doc`으로 문서를 마무리하고, `qa-brief`로 후속 질문 브리프를 만든다.

## 매 단계 공통 규칙
- 구현 전에 계획을 보여주고 사람이 승인한 단계만 진행한다.
- 한 번에 하나의 작은 작업만 한다. 끝나면 바꾼 파일, 이유, 테스트 결과를 3줄로 보고한다.
- 작업 단위가 끝나고 테스트가 통과하면 커밋한다. 메시지: "feat|fix|test|docs: 무엇을 왜"
- 설계 선택은 `docs/decisions.md`에 D# 블록으로(이유, 버린 대안, 감수한 제약) 남긴다.
- 예상과 다르게 동작했거나 막힌 경우는 `docs/decisions.md` "까다로운 케이스"에 남긴다.
- 사람이 너의 제안을 받아들이거나, 고치게 하거나, 버리면 `docs/ai-judgment-log.md`에 판정·근거·계기를 남긴다.
- 구조나 흐름이 바뀌면 `docs/architecture.md`를 코드와 일치하게 갱신한다.
- 자료에 없는 값은 만들지 않는다. 가정은 `docs/decisions.md` 가정 목록에 적는다.
- 판정·계산은 결정론적 코드로, LLM은 요약·설명에만 쓴다.
- 실명·이메일·사번·키는 코드·문서·로그에 남기지 않는다.
- 단계를 넘어갈 때 `AGENTS.md`의 진행 단계 표시를 갱신하고, 세 가지를 점검한다: 합의에서 벗어나지 않았나, 증거 없이 완료 처리한 것은 없나, 너무 순조로워서 놓친 것은 없나.
- 과제 안내에 지정된 파일명·양식이 있으면 그것을 우선한다.
